## 〇、结论速览

1. **论点成立，而且不是新论点。** `P:375` 已把同一分工写成**用户审过的架构结论**：指挥定"哪里"、规则给依据、生成器出几何、
   **队长执行、不让队长规划阵型**，其判据是探针+文献钉死的"**枚举执行满分、开放规划零分**"。快速执行层该做的那部分，
   正是现有模型已经拿满分的那部分。
2. **因此价值定位要从"更好的判断"改成"更高的判断频率"。** 现有快速层的真正亏空不是正确率，是往返延迟：
   实测 p50 = Qwen3-30B **16.2s** / v4-flash **21.6s** / v4-pro **32.5s**（pilot.log 实算）；
   队长派单节奏 16s/单（`P:357`）；队长吞吐不足（`P:363`）。而 Jev 的标称量级是 **~0.3s**（见 §一）。
   这是约 **1/50 ~ 1/100** 的差距，也是本评估唯一真正有分量的数字。
3. **"架构需要有大变化"指向的不是"加一层"，而是三处既有设计前提的同时动摇**（§四）：
   姿态标签制的前提（`P:322`"20s 延迟打不了实时微操"）、看门狗 90s 的存在理由（`P:387` 阈值与 LLM 往返撞车）、
   以及三层指挥链的分层理由（事件触发/心跳/零召唤——部分是为抗延迟而设计）。
4. **唯一待验问题**：在有队长指令的前提下，Jev 的现场判断（该接战否 / 打谁）是否显著优于现有阈值规则？
   若只是"更快"而"不更准"，则要看**频率是否真是瓶颈**——这一问可由现有日志直接量，不需要接任何东西。
5. **状态：待决，未实施。** 本次未写任何验证脚本（用户 2026-09-22 决定）。

## 三、关键发现：把问题从"质量"重构成"频率"

`P:375` 的"枚举执行满分、开放规划零分"把评估轴换掉了：

- 现有模型的**规划能力为零**（所以架构不让队长规划——这是对的）；
- 现有模型在**枚举执行上已经满分**（所以队长的活它干得对——这也是对的）；
- 那么快速执行层剩下的唯一亏空，就是 **16.2s 的往返**。

于是"Jev 值不值得接"这个问题的前半段（**它能不能干这个活**）已经被项目自己的探针回答成"能，这正是它唯一能干的事"——
Jev 不能规划（它连零分都拿不到，它做不了规划这种输出形态），它**只能做枚举执行**。这既是它的限定，也是它在这一点上的合格证。
后半段（**更快有没有用**）才是真正未验的部分，且它取决于一件事：**频率是不是瓶颈**。

**频率是否为瓶颈，可以用现有资产直接量，不需要接任何东西**：`bridge/activity-*.jsonl` + `bridge/pilot.log` 里
"派单等待时间 / 小队决策等待时间 / 等待期间现场变化量"这三项。若等待期现场几乎不变，加快决策无收益；若期待期间目标已移走/已失
（`attack 目标不可达` 这类回执是现成观测点），加快决策直接换到完成率。

## 四、可能的大变化（架构层，逐条）

本节是本文件的核心：延迟塌两个数量级之后，**以下四处既有设计前提需要重新论证**。不是"加一层"，是"已有的几层要不要重切"。

### A. 姿态标签制的前提被动摇（`P:322`）

姿态制的立法理由白纸黑字是"20s 延迟打不了实时微操"。若现场判断变成 ~0.3s，这个前提消失：
姿态制从"唯一解"降级为"一种选项"（或退为不常更新的宏观姿态 + 现场细判并存）。
**这一条如果成立，影响面大于接不接 Jev 本身**——它意味着"确定性层毫秒级执行具体走位"这条分工需要重审。

### B. 看门狗（`squad_watchdog_sec=90`）的必要性塌陷

它的唯一存在理由是 LLM 往返（`P:387` 撞车记录）。往返降到 0.3s 后，看门狗可以从"兜底代打"退成"故障保护"（真死才触发），
"系统代打"与"LLM 迟到"的抢方向盘问题从常态降为异常路径。`P:368` 的 90s、`P:387` 的 90s 两处都要重估。

### C. 队长吞吐瓶颈解除

`P:357`/`P:363` 记录的 16s/单 直接限制建造吞吐（"2 组×4 人×1 单/16s"）。若派单降到亚秒级，
`P:368` 的"每拍至多 3 动作"这类为吞吐打的补丁会变成多余约束，队长分组数（econ/econ2/defense/defense2）也可以重算。

### D. 三层指挥链的分层理由需重证

现结构（总指挥 → 军种中层 → squad chat）里，"事件触发不轮询""心跳""无兵无队零召唤省 token"（`P:261`、`P:387`）
这些机制**有一部分是为抗延迟而设计的**。延迟塌掉后，"层数"的答案可能双向移动：
可以压缩（少一层也不误事），也可以反而加层（每层都便宜了）。`P:333` 的"三级分级汇报"同理——它是按"每层只看该看的"设计的，
但若单次调用极便宜，分级的经济理由减弱。

### E. 反射层重新定位

现在反射层是"毫秒级唯一执行者"（`P:37`）+ 保命豁免（`P:322`）。加入 ~0.3s 的判断层后，
它变成"判断层之下最后兜底"。**毫秒级不可替代这一点不变**（0.3s 仍差三个数量级），但"什么该由反射层管"的边界要重划。

### F. 契约形态与汇报通道改变

现契约是**自由文本 JSON + 工具调用 + `note` 动作**（`P:349` 建造小队契约含 build/move/repair/hold/**note**；
`P:372` note 带时间戳进建造指挥 pending）。Jev 出不了 `note`——它是类型化答案，没有自由文本通道。
所以切进这一层必须同时解决：**汇报（note）由谁承接**（上移到军种中层？还是由确定性层从动作序列生成？）。
这一条是实打实的集成成本，不是纸面问题。

## 五、反面证据（诚实清单）

1. **本项目至今的每一场胜仗都来自"把确定性层做厚"，不是来自"换更聪明的判断器"。**
   `P:381-392`（执行层四连修）、`P:396-405`（实控纪律四连修）、`P:443-467`（平静期三行为 + 按厂科技档产兵）
   全部是 bug 连修与规则层补强。Jev 补的是"判断质量/频率"这条轴，而这条轴不是过去赢球的地方。
2. **`P:288` 有一份范围需要注记的旧裁决**：用户问"脚本配指挥还是指挥配快速执行 AI"，结论"**脚本配指挥**——本案失败在指挥的
   战略判断与闸门的战略深度，快速执行 AI 只会让 builder 死得更快"。**注记范围**：该案是**战略级决定被下放**给快速层
   （要不要派 builder 孤悬敌境），与本评估"深度由队长指令带进来、快速层只做现场适配"不是同一件事。
   本条不否定本评估，但也不给本评估背书——它只是提醒：**"快速层"这个名字下曾经死过一次**。
3. **现状能力**：AI 尚不能稳定战胜最高难度内置 AI，进攻性、建造速度、多线协同仍在打磨（README「当前状态」）。
   已知问题三项（升级动作回执不落地悬案、采集器跟随闭环、反射目标按版本写死）**没有一项是判断问题**。
4. **Jev 看不出 state 里没有的东西。** "看懂当前情况"的成本在本项目里全在**蒸馏层**：阶段 1 地图理解重修、
   迷雾三态/幽灵记忆/可见即真相冷却、`powergrid` 安全值、`danger` 威胁热力、`P:215` 的 `pool:k` 归因。
   **Jev 的上限 = 蒸馏层质量**，它不会让"看懂"变好一分。
5. **官方自认弱项与本项目直接相关**：中文/日韩"稳定性不一"（本项目内容为中文）、精确算术与计数（战力/经济账本，不过这部分本就不该给它）、
   长 state 噪声。`jev-latest` 漂移对"靠阈值自动动作"的系统是真实风险。
6. **零实测。** 本文件所有 Jev 数字都来自外部资料；本项目没有一次调用、没有一个 token 的账。

## 六、必须先定的设计边界（三项，否则会重演旧病）

1. **最终决策权归谁。** 若 Jev 答"现场不可行"而任务书要求打，谁说了算？
   建议口径：**Jev 只回答"现场可行性"，打不打归任务书 + 执行层政策**——分歧变成可审计日志，而不是静默抗命
   （阶段 3 的形态：`P:237` squad 拿"（敌强我弱，勿硬拼）"当抗命借口 56 分钟零指令，修法是军令化 + 删掉那句提示）。
2. **汇报通道。** `note` 是 chat 的产物（`P:349`/`P:372`），Jev 出不了。见 §四 F。
3. **状态口径。** 本队态势 + 可见敌情规模小（不是 `P:278` 那个 336+ 单位摘要问题），但**迷雾语义必须显式进 state**
   （全黑=未知、浅黑=记忆、可见=真实，`P:216` 的四路注入口径），否则 Jev 的判断与单阈值无异。

| 指标 | 该接战否一致率、单位损失、决策延迟、派单吞吐、`attack 目标不可达` 回执率 |
| 判定线 | **只在"现场判断质量显著优于阈值规则"时才值得接入。** 若结论只是"更快"，先答 §三 的频率问题——若频率不是瓶颈，它就是第二个 squad chat |

## 附注：与另一项目（CityLife / 市民圈）的对照

同一天用同一套问题评估了另一个项目（CS2 mod，`D:/CimTalk`），结论是 **Jev 在那里没有位置**：那边的 LLM 只做两件事——
"结构化上下文 → 文本"与"玩家的自然语言 → 结构化意图"，**Jev 两件都做不了**（不生成文本；意图解析那边用执行层规则+确认卡兜住了）。

差异的根因值得记一笔：**那边 LLM 的职责是产文本，这边 LLM 的职责已经被收窄成枚举执行。**
同一个工具落在两个项目上结论相反，不是因为工具不同，是因为**职责的收窄程度不同**——而收窄这件事，
正是本项目 `P:375` 那条"不让队长规划阵型"已经做完的。

### 未决分叉（下次先定）

**建造小队 chat ×4 要不要一起换？**

- 登记在案的吞吐账**都在建造侧**：`P:357` 待办①"**队长派单速度（16s/单）**"、`P:363`"**队长吞吐不足**（2 组×4 人×1 单/16s）"。
  战斗 squad chat 的病是**抗命**（阶段 3），不是吞吐。
- **只换战斗那层，这两笔账不会动。**
- 建造队长**恰好是 Jev 的形状**：契约本身即"从合法锚点表里选点"（探针判定维度含"锚点来自合法表"，`P:348`）。
- 唯一硬约束：**Choice 候选上限 255**——锚点表大了要先 Score 粗筛再 Choice。

### 落地前必须先定（同 §六）

1. **汇报通道**：`note` 是 chat 的产物（`P:349`/`P:372`），**Jev 出不了自由文本** →
   建议由**确定性层从动作序列生成模板化上报**（"S1 连续 3 次判不可行"），既不丢信息又把分歧变成可审计日志。
2. **决策权边界**：Jev 只答"现场可行性"，**打不打归任务书 + 执行层政策**（§六 第 1 条）。
3. **版本 pin** `jev-1.13.0`，不用 `jev-latest`（阈值驱动的自动动作经不起概率漂移）。

### 工程要点

- **`bridge/llm.py` 不可复用**：它是 OpenAI 兼容 chat（`/chat/completions` + tools）；Jev 走 `POST /v1/systemone`（直连）
  或 `/api/alpha/decisions`（OpenRouter），请求 = `state` + 带类型的 `questions`，响应 = `answers`。无 messages / 无 tools / 无流式。
- **并发，别串行**：6 队 × 284ms 串行 = 1.7s，**吃掉 `fast_interval_sec=2.5` 整拍**。Jev 是 HTTP 可并发；
  且一次请求可对同一 state 并行答多题而几乎不加延迟——要么并发发，要么按军种合并成"一个 state + 多题"。

### 一条认识修正

本项目的成本纪律核心是"固定头逐字节稳定吃缓存"（DeepSeek 命中价 = 未命中的 1/50，`P:` §十二相关条目）。
**Jev 没有公开的缓存档**——$0.042/M 是统一输入价。所以"固定前缀 + 动态尾部"依然是好习惯（可测、可预期），
但**在 Jev 这条路上省不到钱**。因调用量小（≈$0.09/局），不影响结论。

### 上线前必须压测

1. **中文稳定性**：官方自认英文最强、中日韩"稳定性不一"，而本项目 prompt 为中文。
2. **校准按原语分别标定**：独立测试校准误差 **Noul 0.012 / Choice 0.086 / Score 0.254**——差一个数量级，一个阈值打不了天下。

### 附：本地部署路径（已否决，留档备查）
